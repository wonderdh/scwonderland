# 02. DB 스키마 설계 · 마이그레이션 관리 (2026-11-02)

> 기준: `supabase/migrations/*.sql` 44개 (미커밋 `20261031000000` 포함) + `src/**/*.ts` 쿼리 코드 + `src/lib/types/database{,.generated}.ts`. 읽기 전용. 원격 DB 미접속.

## 요약

- FK 컨벤션(학생→`students`, 교사→`teachers`, actor→`profiles`)은 최종 스키마에서 위반 0건으로 잘 지켜지고 있고, 최근 버스 3개 마이그레이션은 backfill→정리→NOT NULL 순서가 정석적이다.
- 가장 큰 문제는 `20260615110558_remote_schema.sql`(db pull) 하나가 이전 보안·정합성 패치 **5종**을 되돌린 채 그대로 남아 있다는 점이다. 02-DB리뷰가 잡은 3종 외에 반 명부 SELECT 좁히기 원복과 출결→버스 트리거 reason 보존 원복이 추가로 살아 있다.
- 신규 🔴 2건(반 탈퇴 시 성적표 CASCADE 삭제, 죽은 테이블을 참조하는 고아 트리거)과 🟡 7건(날짜 컬럼 인덱스 누락, time 을 text 로 저장, 소속 이중 저장 등)을 찾았다. 수동 타입 파일 `database.ts` 에는 존재하지 않는 테이블·컬럼을 가리키는 죽은 타입 5개가 있다.

## 🔴 데이터 손상·무결성

**R1. 반 탈퇴 = 성적표 삭제.** `report_cards.class_student_id → class_students(id) ON DELETE CASCADE` (`20260525000000_refactor_classes_periods_schedules_report_cards.sql:114-116`). 앱은 반 구성 변경 시 `class_students` 를 hard delete 한다 (`src/app/(admin)/admin/actions/class-actions.ts:591, 688`, `afterschool-actions.ts:166`). 학생이 반을 옮기거나 방과후를 그만두면 그 반 소속으로 작성된 월별 성적표가 통째로 사라진다. 숙제 진도 CASCADE 는 data-model.md §2.3 에 적혀 있지만 성적표는 언급이 없다.
개선안: `alter table report_cards drop constraint report_cards_class_student_id_fkey, add foreign key (class_student_id) references class_students(id) on delete restrict;` — 또는 반 탈퇴를 `is_active=false` soft delete 로 바꾸고 삭제 경로를 없앤다 (둘 중 하나, 둘 다는 과잉).

**R2. 반 명부 SELECT 좁히기가 원복됨 (02-DB리뷰 미포함).** `20260601020000`/`20260601050000` 이 `classes`·`class_students`·`class_teachers`·`class_schedules` 의 `USING(true)` 를 본인 반으로 좁혔는데, `remote_schema.sql:11-17` 이 그 정책을 drop, `:133-135` 가 헬퍼 `private.my_student_class_ids()/my_teacher_class_ids()` 를 drop, `:509-541` 이 `USING(true)` 로 재생성. 학생이 전교 명부·반 매핑을 다시 볼 수 있는 상태.
개선안: `20260601050000_fix_class_select_recursion.sql` 본문(헬퍼 2개 + 정책 4개)을 새 마이그레이션으로 재적용.

**R3. 출결→버스 트리거의 admin 메모 덮어쓰기 복귀.** 판정표 #9 참조. `remote_schema.sql:191` `reason = v_absent_reason` 가 `20260521010000:48` 의 `coalesce(nullif(...))` 를 덮음. 결석 처리마다 admin 이 적은 reason 이 소실된다.
개선안: `20260521010000` 의 `CREATE OR REPLACE FUNCTION` 블록 재적용.

**R4. 죽은 테이블을 참조하는 고아 트리거.** 판정표 #10 참조. `tg_class_student_reactivate_seed` (`20260509010000:53-56`) 의 함수 본문이 `homework_unit_progress`(`20260516000000:26` drop)·`class_textbooks`(`20260515000000:13` rename)·`textbooks`(`20260519000000:10` rename) 를 참조 (`remote_schema.sql:239-241` 에서 클라우드에도 그대로임을 확인). 코드가 `class_students.is_active` 를 UPDATE 하는 곳이 없어(grep 0건) 현재는 미발화 — 누군가 재활성화 기능을 붙이는 순간 `relation does not exist` 로 UPDATE 전체가 실패한다.
개선안: `drop trigger if exists tg_class_student_reactivate_seed on class_students; drop function if exists tg_class_student_reactivate_seed_units();`

## 🟡 성능·유지보수

**Y1. 날짜 단독 필터 인덱스 없음.** 코드가 날짜만으로 거는 쿼리: `attendance.attendance_date` 13회 (`attendance-actions.ts:109,156,199`, `dashboard-actions.ts:21`), `bus_change_requests.request_date` 6회 (`change-actions.ts:288,790`, `manifest-actions.ts:41`), `bus_check_records.check_date` 7회 (`board-actions.ts:54,133`, `manifest-actions.ts:129`). 세 테이블 모두 UNIQUE 가 `(student_id, date)` 순이라(`baseline.sql:557,567,577`) 날짜 선두 필터에 못 쓴다. 같은 이유로 `student_bus_defaults` 는 PK `(student_id, direction, day_of_week)` (`baseline.sql:662`) 인데 명단 조회는 `(direction, day_of_week)` 만으로 건다 (`manifest-actions.ts:37`). 단일 학원 규모라 체감은 작지만 날짜별 화면이 전부 seq scan 이다.
개선안: `create index on attendance (attendance_date); create index on bus_change_requests (request_date); create index on bus_check_records (check_date);` — `student_bus_defaults` 는 행 수가 작아 보류.

**Y2. 시간을 text 로 저장.** `bus_time_slots.time text` (`baseline.sql:339`), `bus_stop_schedules.estimated_time text` (`:313`). `20260603000000:21` 이 `substring(bts.time from 1 for 5) = '16:20'` 문자열 비교로 1·2차를 판정한다. 정렬·범위비교·형식 검증이 전부 앱에 떠넘겨진다.
개선안: `alter table bus_time_slots alter column "time" type time using "time"::time;` (포맷 통일 확인 후). 당장은 CHECK `time ~ '^\d{2}:\d{2}$'` 한 줄로도 충분.

**Y3. `students.group_type text` 가 enum 과 어긋남.** `students.group_type text` nullable, CHECK 없음 (`baseline.sql:482`). 코드는 한글 라벨 `'유치부' | '오후반'` 을 넣는다 (`user-actions.ts:216,394`). 반면 `classes.group_type` 은 `class_group` enum(`kindergarten/afternoon/...`). 같은 개념이 두 어휘·두 타입. 또 학생의 group 은 소속 반에서 파생 가능한 값이라 중복 저장이기도 하다.
개선안: 최소 `check (group_type in ('유치부','오후반'))`; 장기적으로 `class_group` enum 으로 교체.

**Y4. 방과후 소속 이중 저장.** `enrollStudent` 가 `afterschool_enrollments` INSERT 와 `class_students` upsert 를 함께 수행 (`afterschool-actions.ts:122-134`), 제거 시에도 양쪽을 따로 지운다 (`class-actions.ts:584-591`). DB 제약으로 둘의 일치가 보장되지 않아 한쪽만 지워지면 "반에는 있는데 요일이 없는" 학생이 생긴다.
개선안: `afterschool_enrollments` 에 `class_student_id → class_students(id) on delete cascade` 를 두고 `(class_id, student_id)` 쌍을 거기서 파생 — 또는 `class_students` 쪽을 트리거로 동기화. 현재 코드 패턴을 바꾸지 않을 거면 최소 코멘트.

**Y5. 시간대 삭제가 학생 기본 배정을 지움.** `student_bus_defaults.bus_time_slot_id → bus_time_slots ON DELETE CASCADE` (`baseline.sql:1061`) 인데 같은 테이블의 `bus_stop_id` 는 SET NULL (`:1056`). 코드는 시간대를 soft delete 한다 (`master-actions.ts:84`) 라 실발동은 안 하지만, 콘솔에서 행 하나 지우면 전교 기본 배정이 소리 없이 사라진다.
개선안: `on delete restrict` 로 교체.

**Y6. `bus_stop_schedules.bus_number_id` nullable.** `20261015120000:32-33` 이 nullable 로 추가하고 backfill 했지만 NOT NULL 로 올리지 않았다. 짝인 `bus_stop_day_assignments.bus_number_id` 는 NOT NULL (`baseline.sql:296`). UNIQUE 가 `NULLS NOT DISTINCT` 라 NULL 호차 행이 "호차 미지정 도착 시각" 으로 공존 가능 — 20261015130000 이 시간대 NULL 을 없앤 취지와 어긋남.
개선안: `delete from bus_stop_schedules where bus_number_id is null; alter table ... alter column bus_number_id set not null;` (NULL 잔존 건수 먼저 확인).

**Y7. 되돌릴 수 없는 삭제에 사전 집계 없음.** `20261015130000:24-25` 가 fallback 배정·도착시각 중 학생이 안 타는 행을 조용히 DELETE (sort_order 소실), `20261031000000:7-9` 가 컬럼 2개 drop. 두 파일 모두 `raise notice` 나 건수 가드가 없다 (`20260528000000:19-33` 의 가드 패턴과 대조). 이전 지적(REVIEW_DB §6.2) 은 숙제 도메인 truncate 였고 버스 쪽은 신규.
개선안: 삭제 직전 `do $$ ... raise notice '% rows', count $$` 한 블록.

**Y8. `database.ts` 수동 타입과 스키마 불일치.** 이 파일은 generated 를 덧씌우는 게 아니라 별도 sidecar 다 (`index.ts:1-15` 가 re-export, 앱 코드는 `Database` 를 generated 에서 직접 import). 그중 스키마와 어긋난 것:
- `ClassSchedule` (`database.ts:130-140`): `class_id: string | null`(DB NOT NULL), `student_profile_id`·`teacher_profile_id`(존재하지 않는 컬럼; 실제는 `class_teacher_id`). import 하는 곳 0건.
- `BusCheckRecord` (`:75-85`): `bus_time_slot_id: string`, `checked_at: string` — DB 는 둘 다 nullable (`baseline.sql:269,272`). import 0건.
- `AfterschoolEnrollment` (`:120-126`): `second_period` 없음 (`20260603000000:9-10`). import 0건.
- `Textbook` (`:167-180`): `series`·`total_units`·`cover_image`·`description` — `homework_books` 에 없음 (`20260529000000:129-131` 에서 drop). import 0건.
- `LearningRecord` (`:30-42`): 대응 테이블 없음. import 0건.
- `BusStopDayAssignment.bus_time_slot_id: string | null` (`:92`) — `20261015130000:28` 이후 NOT NULL. 이건 사용 중 (`master-actions.ts:299-314`).
개선안: 위 5개 dead type 삭제, `BusStopDayAssignment.bus_time_slot_id: string` 으로. 가능하면 `Tables<"...">` 로 대체.

**Y9. 이전 지적 — 해결 여부.**

## 🟢 네이밍·취향

- **G1.** `seed.sql` 참조 누락: `config.toml:65` `sql_paths = ["./seed.sql"]` 인데 파일이 없다. `scripts/sync-full.sh` 가 `db reset` 을 돌리므로 CLI 버전에 따라 경고/실패 가능 (추정). 개선안: `sql_paths = []`.
- **G2.** `remote_schema.sql:5` `drop extension if exists "pg_net"` — db pull 노이즈. 재적용 시 클라우드에서 pg_net 을 지운다. 사용 중이 아니면 무해하지만 의도 없는 drop 은 지워두는 게 안전.
- **G3.** 마이그레이션 번호: raz 파일이 `20260813000000 → 20260815074049` 로 rename 되어 클라우드와 맞춘 이력(`9d877b5`)이 있고, `20260525000000:13`·`20260526001000:14` 가 "이미 수동 적용됨" 이라 적혀 있다. 레포 번호와 클라우드 `schema_migrations` 가 어긋난 전례가 둘 → 판정표 #11 과 함께 `supabase migration list` 로 1회 대조 권장.
- **G4.** `bus_check_records` UNIQUE `(student_id, check_date)` 는 "하루 1회 체크" 가정이다. 코드도 dropoff 만 체크해서(`board-actions.ts:21-29,98-107`) 현재 맞지만, 등원 체크를 붙이면 즉시 깨진다. 테이블 코멘트 한 줄 권장.
- **G5.** 이전 지적(REVIEW_DB §7.1~7.5): `textbook_id` 네이밍, `class_teacher_id` 참조 불일치, 요일 0..6 vs 1..5 혼재, 인덱스 이름 `idx_` vs `_idx`, enum vs text+CHECK, soft delete 이원화 — 모두 미해결, 현 상태 동일.

## 잘 되어 있는 점

1. **최근 버스 마이그레이션의 전환 순서** — `20261015120000`(nullable 추가 → 앱 로직과 동일한 해석 순서로 backfill) → `20261015130000`(실사용 fallback 만 전용 배정으로 승격 → 나머지 삭제 → NOT NULL) → `20261031000000`(레거시 drop, 코드·타입 동시 정리). 교과서적 expand/contract.
2. **FK 컨벤션 0건 위반 유지** — 2026-05-12 일괄 교체 이후 신규 테이블(lunch, closed_days, raz) 전부 처음부터 `students/teachers/profiles` 를 올바르게 구분. `raz_read_logs_insert` 가 `marked_by = auth.uid()` 를 RLS 로 강제하는 것도 actor 컬럼 무결성을 DB 가 책임지는 좋은 예.
3. **데이터 교정 마이그레이션의 가드** — `20260528000000:19-33` 의 `bad_count > 0 → raise exception`, `20260526001000:49-54` 의 UNIQUE 충돌 회피 `NOT EXISTS`, `20260530100000` 의 이름 파싱 실패 시 `raise notice + continue`. 이 패턴을 Y7 의 버스 삭제에도 그대로 쓰면 된다.
