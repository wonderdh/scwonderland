# SC Wonderland — 영어 학원 관리 시스템

원생 171명, 교사 10명이 쓰는 학원 운영 웹. 종이 명단과 기억에 의존하던 하원 버스 배정에서 시작해 출결, 반 편성, 급식 지도, 숙제 검사, 리딩 기록, 리포트 카드까지 옮겼다. 2026년 1월 28일 첫 커밋, 기획·설계·개발·운영 1인.

**스택**: Next.js 16 (App Router) · React 19 · TypeScript · Tailwind v4 · Supabase (Postgres, Auth, Realtime, Storage) · DeepL API

## 1. 문제

하원 버스에 학생을 태울 때 출입문에 붙인 A4 명단과 기억으로 호차를 정했다. 학부모의 당일 변경은 전화·문자·메신저로 한 사람에게만 전달돼 명단과 어긋났고, 주 5일 중 3~4일은 잘못 탑승하는 일이 생겼다. 개인의 부주의가 아니라 변경 사항이 한곳에 모이지 않는 구조의 문제로 봤다.

## 3. 구조와 설계 이유

```
브라우저 ──► proxy.ts (세션 쿠키 갱신만, 차단 없음)
         ──► layout.tsx (역할별 문지기: admin / teacher / student)
         ──► Server Action (쓰기 창구, 첫 줄에서 인증 검증)
         ──► Supabase Postgres (RLS 정책이 2차 방어)
```

- **쓰기는 Server Action 한 곳으로**. `(admin)/admin/actions/` 아래 도메인별 1파일. 모든 mutation은 첫 줄에서 `verifyAdmin` / `verifyTeacherOrAdmin` / `verifyAuthenticated` 중 하나를 호출한다. 예외는 `// @auth-skip: <이유>`로 명시해야 CI(`check:action-auth`)를 통과한다.
- **Supabase 클라이언트 3종 분리**. 브라우저용(anon), 서버 세션용, service role용. service role은 서버 전용이고 클라이언트 번들에 들어가면 CI(`check:admin-imports`)가 막는다.
- **RLS는 이중 방어**. 앱 코드가 권한을 틀려도 DB가 한 번 더 막는다. 학생은 자기 것만, 교사는 자기 반, 관리자는 전부.
- **파생 데이터는 DB 트리거**. 출결→버스 명단 동기화, 반 배정 시 숙제·진도 초기 행 생성처럼 "항상 같이 바뀌어야 하는 것"은 앱이 아니라 DB가 보장한다.
- **스키마 변경은 마이그레이션 파일만**. 적용 후 `pnpm db:types`로 TypeScript 타입을 생성해 코드와 DB가 어긋나면 컴파일에서 잡힌다.
- **Repository 계층 없음**. 1인 개발, 운영 1곳이라 Server Action이 Supabase를 직접 호출한다. 추상화 비용보다 읽기 쉬움을 택했다.

## 5. 사고와 복구

**6월 보안 패치가 조용히 되돌려졌다.** 6/1에 RLS 정책 5종(학생 셀프 승인 차단, anon 권한 회수, 반 명단 열람 제한 등)을 적용했다. 6/15에 `supabase db pull`로 받은 `remote_schema.sql`이 패치 이전 상태를 담고 있었고, diff 리뷰 없이 머지돼 4개월 넘게 운영에 남았다. 결과: 학생이 전교 반 명단을 볼 수 있었고, 결석 처리 시 관리자 메모가 지워졌다.

11/2 코드베이스 전체 리뷰(8개 축 병렬 조사, `docs/2026-11-02/`)에서 발견했다. 조치:
1. `20261102000000_restore_june_security_patches.sql` — 6월 패치 본문 재적용 + 승하차 액션 권한을 `verifyTeacherOrAdmin`으로 격상.
2. CI `check:migration-danger` — 정책·트리거·테이블 삭제나 anon 권한 부여가 든 마이그레이션은 파일 맨 위에 `-- reviewed-by: <이름> <날짜>`가 없으면 실패.
3. `report_cards → class_students` CASCADE로 반 이동 시 성적표가 삭제되던 것을 soft leave(`is_active=false`)로 교체.

그 밖에 5/1 커밋에 service role 키가 평문으로 들어간 것을 5/2에 env로 옮기고 키를 교체했다. 이력에는 남아 있고, 폐기된 키다.

## 6. 현장 피드백으로 바꾼 것

출입문 TV를 처음 걸었을 때 매일 학생을 태우는 분들의 반응은 "없어도 잘한다"였다. 원장 허락은 받았지만 실제 쓸 사람에게 먼저 묻지 않은 것이 시작이었다. "몇 주만 써 보고 불편하면 치우겠다"고 제안하고, 화면에 관한 의견은 전부 받았다.

- 3/10 bus-monitor v3·v4 — 초기 화면 반복 수정
- 4/14 등원 기능 제거, 하원 전용으로 단순화 — 실제로 쓰는 건 하원만이었다
- 4/15 시니어 친화 UX 개편 — 글씨 키움, 터치 타겟 확대, 상태 뱃지, 내비 그룹화. 사용자 다수가 50대 이상

정보를 줄이고 글씨를 키운 뒤 자리를 잡았다.

## 7. 검증

CI (`.github/workflows/ci.yml`) 7단계: `check:admin-imports` → `check:action-auth` → `check:migration-danger` → `type-check` → `test` → `lint` → `build`.

유닛 테스트는 순수 로직 5곳만 (정류장 미배정 판정, 리딩 통계, 숙제 스케줄, 주차 계산, Raz 변환). UI·Server Action 테스트는 없다. 대신 정적 검사 3종이 "권한 검증 빠뜨림", "service role 유출", "위험한 마이그레이션 무심사"라는 실제로 겪은 사고 유형을 막는다.

## 8. 한계

- 테스트가 적다. 액션·UI 회귀는 수동 확인에 의존한다.
- 리뷰 지적 사항 처리가 늦었다. 4~7월 리뷰 163건 중 11월 전까지 14건만 처리. 11월에 즉시 조치 5건을 먼저 끝냈다.
- 레거시 Server Action 다수가 `ActionResult` 타입(`{ok, data} | {ok, error}`)으로 이관되지 않았다. 새 코드부터 적용 중.
- 학원 1곳 전용. 멀티테넌트 아님.
- 화면 캡처 없음 (운영 데이터라 더미 데이터 캡처 예정).

## 9. AI 도구 사용

구현의 상당 부분을 Claude Code와 함께 했고 커밋의 약 2/3에 공저 표기가 있다. 내가 한 것: 무엇을 만들지, 어떤 현장 의견을 받아들일지, 어느 설계를 보류할지(예: 등원 기능 제거, Repository 계층 안 둠), 어떤 리뷰 지적을 먼저 고칠지. 도구가 한 것: 구현 속도, 전체 리뷰의 병렬 조사, 반복 리팩터링. 도구가 낸 코드는 CI와 리뷰 보고서로 검증했고, 6월 사고처럼 검증을 건너뛴 곳에서 문제가 났다.

## 로컬 실행

```bash
pnpm install
cp .env.example .env.local   # NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY, DEEPL_API_KEY
pnpm dev
```

운영 DB → 로컬 동기화 절차는 `docs/db-sync.md`. 폴더별 작업 규칙은 각 `AGENTS.md`, 전체 규칙은 `CLAUDE.md`.
